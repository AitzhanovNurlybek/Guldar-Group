# Backend — GulDar Group API

FastAPI · Pydantic Settings · SQLAlchemy

## Запуск

```bash
cd backend
python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # macOS / Linux
pip install -r requirements.txt
cp .env.example .env            # заполнить значения
uvicorn app.main:app --reload --port 8000
```

- API: http://localhost:8000/api
- Документация (Swagger): http://localhost:8000/docs

## Тесты

```bash
python -m pytest -q
```


## Эндпоинты

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/health` | проверка, что сервис жив |
| GET | `/api/ready` | проверка доступа к БД; `200` при готовности, `503` при сбое |
| POST | `/api/leads` | сохраняет заявку и возвращает реальный ID после commit |

Локально таблица `leads` создаётся автоматически в SQLite при первом обращении. Для production настройте `DATABASE_URL` на PostgreSQL, например `postgresql+psycopg://...`; драйвер входит в зависимости. Пользователь БД должен иметь право создать таблицу при первом запуске. Схема создаётся через `create_all`, последующие изменения схемы потребуют миграции.

На Vercel (`VERCEL=1`) и при `ENVIRONMENT=production` SQLite запрещена: файловая система функций не подходит для постоянного хранения заявок. Без доступной внешней БД API вернёт `503` и предложит WhatsApp. При ошибке транзакция откатывается; ответ и логи не раскрывают SQL, телефон или реквизиты подключения. Уведомления менеджеру ещё не подключены. Формы сайта по-прежнему готовят сообщения WhatsApp.

Инициализация соединения защищена от одновременного старта запросов и повторяется после неудачной попытки. `pool_pre_ping` обнаруживает закрытые соединения. На Vercel используется `NullPool`, чтобы экземпляры функций не удерживали лишние соединения. В обычном процессе пул ограничен 5 соединениями и 5 дополнительными. `DATABASE_CONNECT_TIMEOUT` и `DATABASE_POOL_TIMEOUT` задают ожидание подключения и свободного соединения; они не ограничивают время выполнения SQL. Автоматических повторов записи нет: неоднозначный результат commit не должен создавать дубликат заявки.

Валидация тела запроса выполняется до открытия БД: неверные данные возвращают `422`, даже если хранилище недоступно. `/api/health` работает независимо от БД. `/api/ready` выполняет `SELECT 1` без создания тестовых заявок. Эти ответы и ошибки хранилища не кешируются; `503` содержит `Retry-After: 60`.

Тесты используют временную SQLite-базу: сохранение и повторное подключение, валидация и границы полей, уникальные ID, rollback, недоступная БД, запрет SQLite на production, CORS и отсутствие публичного чтения заявок. Дополнительно проверяются 24 параллельные заявки, одновременная холодная инициализация, таймаут ожидания, восстановление после сбоя и закрытого соединения. Настройки PostgreSQL проверены через подмену фабрики; подключение к внешнему production PostgreSQL требует отдельных учётных данных и проверки `/api/ready` после развёртывания.
